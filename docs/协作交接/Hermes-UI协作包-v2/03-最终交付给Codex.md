# 最终交付给 Codex：可运行、已确认、可接续的 UI 交接包

版本：v2 · 2026-10-24。此文件把用户已明确提出的最终交付要求纳入本次协作。它描述将来要产出的内容，不代表设计已获确认或已经验证。

## 1. 最终目标

让没有参与 Hermes 原对话的 Codex 能打开用户确认的 UI，知道哪些特征要保留、每个操作应如何表现，并按正式项目已有控制器、接口和角色分工继续接入。

Hermes 完成设计收敛与原型交接；无需为了交付而把后端全部实现。可运行原型可以是单 HTML，也可以是前端项目，不要求为了交接改框架。

用户确认一个阶段后，可以交该阶段完整且边界清楚的版本，不必等待所有未来页面结束。未完成项如实记录。

## 3. 交互与状态怎样说明

状态表建议包含这些列：

```text
ID | 页面/状态 | 进入条件 | 用户看到什么 | 可操作项 | 操作后的状态
   | 原型行为 | 正式产品预期 | 组件/文件位置 | 示例标记
   | 确认状态 | 截图/预览入口 | 尚缺事项
```

三种状态含义必须明确：

- **原型真实可用**：例如展开来源、切换已准备好的样例、打开抽屉。只说明这个本地交互可用，不推断真实服务可用。
- **模拟**：计时播放的调查过程、合成结果或预置通知等，标为 `controlled_fixture`，保持可见原型标记。
- **未实现**：按钮占位、尚无数据流、未来 API 接入。不能用无反馈按钮装成已完成。

覆盖输入、必要澄清、调查中、结论与来源、未知/冲突、伴读、历史更新、盯梢，以及取消、失败、空结果、部分结果、到限等相关状态。既有 PRD 中没有变更授权的行为不自行改动。未做项写清，不要求每个状态一张精修截图。

## 4. 源码、规则与截图如何保持一致

用户确认阶段版本后，冻结交付副本。在该副本上生成截图和检查结果，并记录交付版本。之后再修改就生成新版本，不把旧截图当新版本证据。

至少准备：一个最终主界面、一段关键交互、一个异常/边界状态、一个手机核心状态。使用同一明确标记的代表案件，包含足够长的中文、多来源和未知/冲突；避免截图全部是理想短文案。

用户偏好写成“哪个位置、为什么喜欢、哪些场合沿用”，不要只写“高级、简约、有侦探感”。数值以真实源码为依据；不要从截图凭空推导并写成已确认值。

## 5. 交回前的验收

### 必须检查并报告

1. **版本确认**：用户认可的页面与将要打包的源码、规则、截图对应；明确用户确认的范围。
2. **独立目录启动（M1）**：从交付包复制/解压到新目录，按 START-HERE 的步骤打开。前端项目按锁文件使用所需运行时；没有依赖的 HTML 不额外引入工具。记录实际命令、结果和错误。
3. **关键操作**：走一遍主要原型流程，核对错误/空结果/长内容/手机行为；模拟和未完成部分明示。
4. **依赖与文件完整性**：没有只能在队友私人路径找到的必要文件；源码可编辑，不只有 dist、截图或在线临时预览地址。
5. **缺口清单**：接口需要什么、哪些动作待正式接入、已知视觉问题、尚未确认的选择清楚可查。

没有条件执行某项检查时，写明“未执行”和具体原因，交付为“待验证”，不能写通过；也不因此删掉已有成果。

### 分开记录，不强行假定已完成

|阶段|本轮要求|
|---|---|
|M1：成果可打开|Hermes 尽量在独立目录实际验证并报告；异机打开可由收件方复核|
|M2：新会话可接续|可在交付前演练，或由 Codex 接收后验证；未做就写待验，不凭复述规则判通过|
|M3：正式产品接入|本轮不要求 Hermes 完成；交回 Codex 后按角色分工进行|

M2 的有效验证是：新会话只读交接包，完成一处指定小改动和一个未展示状态，用户检查风格与行为是否延续。需要原作者临时补充解释，说明包仍有缺口；补进文件后再核验。

## 7. Codex 收到后应怎样接手

先核对正式项目 README、AGENTS、当前分支、写入所有权和真实接口状态，审查交接完整性，打开交付网页并对照确认截图。复用可用代码和素材，列出必须适配的框架/接口差异；不以集成为由自由重设计。

正式接入由唯一 W 与 P 按已有契约协同。缺少派发或出现会改变用户行为的取舍时，只询问阻塞项；已明确的可执行部分继续推进。接入后的浏览器、移动端、真实数据及错误状态验收单独报告。
