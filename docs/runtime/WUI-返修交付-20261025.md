## 修复与边界

### Failed 不是可恢复的中断

现场核对当前 RunStore：普通 resume 只允许 cancelled/interrupted，必须保留原预算窗口，watch run 不能经普通 resume。UI 现在仅对符合这两种状态的普通任务显示恢复按钮；failed 有/无旧报告均不再显示或发送 resume/add_budget 作为重试。

failed 显示安全的失败说明，保留旧报告、引用/复制和当前状态，提供“新开一桩”；点击只进入新案件输入页，不自动创建或执行调查。取消/中断合法恢复仍保留，新增真实持久 SQLite 宿主重启→interrupted→同窗口 resume 浏览器用例，不把修复做成禁用所有恢复。

### 取消页的失败、pending 与未知提交

新增只读 `TaskFeedback`，在无报告 cancelled、failed/interrupted 和有旧报告停止态统一显示安全错误、提交 pending、只读加载/未知状态及“重新读取状态”入口。提交中禁重复操作；未知且读取失败时禁恢复，重新读取只执行 GET，不重发 POST、不换 key、不说任务仍在后台调查。

复审进一步验证：同案 `open()` 原先会清掉 unknown submission；若手动 GET 再次失败，旧 cancelled 任务会错误恢复可提交。先补控制器失败回归，实际得到 `submission:null / recoveryIncomplete:false`，再修为同案保留 unknown，读取抛错设置 recoveryIncomplete=true，控制器 start 自身也拒绝。成功重读才解除门禁，旧逻辑记录和原 key 保留；显式重试仍用同 key，不能凭只读成功宣称先前 POST 响应已确认。

浏览器受控场景：取消→resume503（pending 禁用，失败可读）→用户明确再试断网→自动 GET 失败→手动 GET 再失败，按钮仍禁用且 unknown 保留→手动 GET 成功（POST仍2次）→用户明确恢复成功。最终3次 resume 使用同一幂等键，受控业务仅实际执行2次，无自动重发。

### 原问题上限恢复到既有4000

公共源码实际名称为 `CreateInvestigationSchema` / `InvestigationPublicSchema`，originalQuestion 已支持 trim 后最多4000；没有反向修改 shared。UI 校验、计数和提交按4000对齐，501/4000原文可完整送到实际HTTP并在刷新后保留。

不再由原型的 `maxLength=500` 在用户输入阶段静默截断。超过4000时保留完整输入、显示与字段关联的安全错误（aria-invalid/aria-describedby），禁止开查，提交函数也检查边界，HTTP client 原有 schema 继续兜底；4001场景没有任何案件POST。计数按去除首尾空白后的原问题，与现有 schema 对齐。没有改原型归档、CSS、颜色或布局方案。
