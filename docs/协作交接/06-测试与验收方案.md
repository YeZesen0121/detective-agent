# 测试与验收方案

日期：2026-10-24。适用于所有模块任务书。当前只有规划，没有产品代码、可执行测试或通过报告；本文件不启动开发。人员按07/08/09号待办执行，UI按10号文件隔离，目标与阻塞按11号文件交接。

## 1. 已确认的方向

- 用户白天基本可参与，晚上需要睡觉，不安排夜间人工值守。
- 用户选择：Agent 基于参考资料提出方案和案例结果，用户审查调查合理性、结论可信度和体验；争议再深入讨论，不逐条批准实现细节。
- 四项调查能力必须测试。参考项目和技能是方法依据，不能替代本产品的运行证据。
- 需求门槛来自 [PRD v1.0 第12节](../AI开发需求文档.md)，现有 [25个样例](../调研验收样例.md) 仍全部为待测。按 AC01–15 建映射，不以总体平均分抵消关键失败，不为了赶工暗删验收项。

## 3. 五层测试及执行时机

| 层次 | 方法 | 何时运行 | 能证明什么 |
| --- | --- | --- | --- |
| 规则与状态 | Vitest；固定数据、受控时间与失败注入 | 模块改动、PR | 预算、去重、状态、引用ID、版本绑定等逻辑满足约束 |
| 接口与持久化 | Fastify inject、真实测试数据库、共享契约 | 跨模块接口/存储变更 | 前后端字段一致、权限有效、数据与幂等正确 |
| 完整用户路径 | Playwright 连真实本地前后端；外部供应商边界可模拟 | 相关PR、合并后 | 查询→澄清→调查→查看来源→追问/停止等流程可用 |
| 调查质量 | 固定证据集配真实模型；另跑真实元宝与读取 | 引擎/提示词/模型变更、正式验收 | 模型能否正确使用证据；真实链路是否具备实际召回与查证能力 |
| 发布与体验 | 实际部署、桌面与手机操作、实际音频、关闭浏览器的后台检查 | 候选发布版本 | 环境与用户使用闭环成立；本机通过不替代部署验证 |

每条测试明确 `controlled_fixture` 或 `live`，另标模型、搜索、正文读取、视觉、TTS哪些是真实、哪些为模拟。禁止只有前端假数据的演示被描述为端到端通过。

## 4. 四项调查能力如何判定

| 能力 | 核心检查 | 明确失败示例 |
| --- | --- | --- |
| 查询规划 | 拆出可查命题，识别对象/时间/条件；缺关键对象时追问；搜索有用途且预算有限 | 活动名未知就任意选活动；为凑次数反复搜同义词 |
| 材料处理 | 区分原文/摘要、支持/反对/背景、转载/独立来源；对齐时间与适用条件 | 三篇转载算三份独立证明；新发表的旧闻当新事件 |
| 可信回复 | 核心主张对应实际证据；限制和未知完整；不确定时给有用的下一步 | URL真实但不支持旁边结论；无证据却判定为假；伴读把可能改成确定 |
| 多步调查 | 有证据缺口才补查；记录补查目的及新增资料；知道何时结束 | 没解决缺口却声称全面核实；达到上限后继续新增付费调用 |

判定看外部可见查询、工具结果、证据与状态，不要求输出模型隐藏思维过程。避免把预设搜索路径写成唯一正确答案。对“最新”使用带查询时刻的来源核对，不能把今天事实永久硬编码为标准答案。

首轮用 T01/L01/F01 跑三种模式，再用 T03/T04/F03、X01/X05/X06/X07 等覆盖关键反例；这只是执行顺序，不替代完整 AC 门槛。关键非确定性案例建议至少3次独立运行并保存全部结果，记通过次数/总次数，不挑最好一次。该数量只用于初步发现波动，不代表统计可靠性；实际付费数量由预算控制。

程序检查可验证字段、引用存在和预算；模型辅助评审必须指出具体主张、来源段落和违反标准，不能只给总分。主 Agent 复核关键引用，用户抽查重要及争议案例。换一个模型或 Agent 审核仍可能同错，不视为独立事实证据。

## 6. 每个任务的可执行测试说明

G0 创建代码骨架时，总集成 Agent 必须建立并实际核对以下脚本；目前只是计划接口，不能宣称这些命令已经存在或可执行：

- `npm run typecheck`：类型检查。
- `npm test`：规则、状态、接口与存储测试；按目录运行的参数需与实际脚本一致。
- `npm run build`：构建。
- `npm run test:e2e`：受控第三方响应下的完整用户路径。
- 调查质量与真实接口评测的入口由 G0 固定，并写入操作文档，包含案例选择、次数、费用上限和输出目录。

每份模块交接补齐：工作目录、依赖与启动命令、测试数据准备/清理、所需环境变量名称、确切测试命令、预期行为、失败判定、报告路径、费用边界。密钥值不写入文档。测试只操作隔离测试数据。

新增功能覆盖成功与关键失败路径；修复缺陷保留能重现原失败的回归测试。不得删断言、跳过核心场景或放宽标准来制造通过。覆盖率只辅助找遗漏，不作为调查质量证明。

## 7. PR、合并和发布

1. 开发 Agent 自测并提交 PR，注明基础/当前 commit、对应 AC、实际命令、退出码、通过/失败/跳过数量与报告。
2. 主集成 Agent 检查需求覆盖、关键实现与测试有效性；在最新集成版本重新验证受影响路径。测试与被测代码出自同一 Agent 不能成为免审理由。
3. 普通 CI 无密钥运行受控测试；真实 API 用量设独立限额，不对每次提交无限触发。
4. 正式验收另附真实元宝、来源核对、设备与后台闭环证据。测试报告绑定 commit、模型/提示词版本、时间和环境；改动后旧证据不能冒充新版本通过。
5. 发现关键结论无证据、串用户数据、预算失控、伪造来源/真实调用、旧报告被改写等问题，该相关门槛失败，修复后复验。外部服务不可用记受阻，不伪造通过。

## 8. 用户关注事项与夜间建议

用户只需要审查三类材料：

- 案例卡：原问题、实际答案、关键证据摘录与链接、未解决问题；判断有没有误导、追问是否必要、下一步是否有用。
- 可操作页面或短录屏：能否快速找到结论、依据、未知和继续入口；伴读是否方便。
- 决策单：具体阻塞、已尝试方法、选项、推荐、对范围/费用/时间的影响。登录、购买和产品取舍集中提交，普通报错先由 Agent 排查。

建议夜间只继续已经确认边界内的开发与有预算测试；遇到需要用户决定的事项保存状态，推进不依赖它的工作。不得自行扩范围、追加费用或将受阻记为完成。目标模式的 Token 限额与供应商费用上限分开设置；本地机器休眠/断网会影响持续执行。

队友按详细待办完成接入、启动/恢复和登录授权；无法独立完成时交主Agent整理最短操作单，按11号文件转交，不假设两位已熟练。面向用户的行动规划见[你的详细待办](07-你的详细待办.md)。
