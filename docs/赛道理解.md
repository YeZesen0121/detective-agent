# 侦探赛道理解：让用户能沿着证据检查 AI 的回答

依据：[赛道文章](https://mp.weixin.qq.com/s/4i4hQB0oX3ED6PVwGwSC2w?scene=1)，发布于 2026-10-20；整理于 2026-10-24。已读取全文、10 张图片，并进行从页首到页尾的滚动截图核验。[原文归档](赛道资料/原文全文.md)｜[图片文字与核验记录](赛道资料/图片文字与核验记录.md)。

本文用 **【原文明确】、【据此推断】、【建议】、【待确认】** 区分规则、理解和实施选择。文章是一份赛道招募说明，兼有工具介绍和入门教程；不是完整赛事章程，也没有量化评分表。以下不虚构评分比例，不把建议写成报名门槛。

我的核心理解：这条赛道希望参赛者把公开信息检索变成可用的查证体验，让 AI 在给出答案的同时，交代依据、来源与不知道的部分。搜索必须实际参与结论形成，用户应当能追溯关键判断。

## 1. 先整理文章提供的示例

### 1.1 开篇的三个失败场景

| 原文场景 | 失败是什么 | 对参赛作品的启发【推断】 |
|---|---|---|
| 问楼下火锅店是否营业，AI 回答营业到晚 10 点，实际已搬迁 | 旧信息或猜测被说成当前事实 | 核对对象、地址和信息时间；无法查证当前营业状态时保留不确定性 |
| 问“那个讲法医的女主剧”，AI 编出不存在的剧名 | 用不完整记忆补出虚构答案 | 提取线索，检索候选，说明匹配与不匹配之处，不强行给唯一答案 |
| 请 AI 辟谣“隔夜开水千万别喝”，AI 附和“有一定道理” | 未发现自己的判断可能错误 | 对待核验说法寻找依据；不把用户的问题本身当成事实 |

这三段是文章的情境化示例，未附实验过程，不能称为作者经过记录的实测结果。本文也不对其中健康说法作事实裁决。

### 1.2 三类基础方向

| 方向【原文明确】 | 文章给的题目 | 原文期待 | 成品呈现建议 |
|---|---|---|---|
| 查真假 | 微波炉热过的饭会致癌？网红锅真的一个蛋都不粘？ | 在转发、下单之前查一遍，带权威来源；可做查证卡，给真／假／说不准 | 明确核查的是哪一句话、什么条件；结论和支持它的证据放在一起 |
| 查最新 | 今天发生了什么？演唱会还有没有票？ | 从最新公开信息寻找答案，标查询时间和来源 | 区分“本次查询时间”和“来源发布时间”；不把“页面曾显示有票”说成此刻保证可买 |
| 查模糊 | 那个谁演的剧、想不起名字的老游戏、一句歌词 | 顺着零碎线索找答案 | 给候选及匹配依据；线索不足可以追问或说明不能确定 |

原文把它们称为灵感方向，**没有要求三类全做**，也没有限定选题只能来自这三类。页面允许网页、机器人、Skill、应用、小游戏；教程部分还提到浏览器插件和朋友对战的真假新闻小游戏。形式开放的共同条件是搜索处于核心。

### 1.3 三类进阶选做

| 进阶能力【原文明确】 | 具体含义 | 对应提交证据【原文明确】 | 易混淆之处【推断】 |
|---|---|---|---|
| 深度调查 | 把问题拆成几步调查 | 一份调查报告 | 长回答不自动等于调查；需要能看出问题拆解、证据和判断 |
| 持续盯梢 | 信息变化时提醒用户 | 一次真实触发的提醒 | 只展示定时任务配置或手动弹通知，不能充分证明真实变化触发 |
| 截图查证 | 丢一张群聊截图就能核对 | 截图查证录屏 | 识别截图文字只是输入步骤，还需查证其说法 |

原文明确这些“选做，做到了评委会明显加分”。没有要求三项都实现，也没有给出每项分值。

### 1.4 商业接入案例与基础教程

文章称腾讯视频接入后补上实时外网信源，增强复杂描述理解和信息召回；把“那个讲法医的女主剧”转化为“提取线索—发起搜索—列候选及出处”的作品启发。配图并未给出真实剧名或查证记录。

文章还列出 WorkBuddy、ima、腾讯视频、腾讯金融科技，并转述官网案例：ima 信源召回提升 10%，腾讯金融科技一周搭建金融搜索能力。这些是文章用于说明工具已有应用的案例，**不是我们的作品指标，也不是本次独立验证的效果**。

入门教程的顺序是：开通元宝搜索 → 用户问题先进入搜索，取回带链接的结果 → 模型根据证据回答。示例提示词要求先回答、简述理由、关键说法后附来源；查真假用真／假／说不准；无依据就说明没查到可靠来源。图 08 与正文一致。

## 2. “踩分点”：明确要求和评审关注点

### 2.1 先满足交付与资格

| 项目 | 性质 | 如何检查 |
|---|---|---|
| 一个能打开的作品 | 明确交付要求；海报还写“能用作品” | 评委能进入并完成一次实际查询，不仅有介绍页 |
| 3 次真实查询的录屏或截图 | 明确交付要求 | 三次查询分别有输入、结果及可追踪来源；输入展示属于建议，结果和可打开来源是原文要求 |
| 每次有查到的结果、点得开的来源链接 | 明确交付要求 | 逐个点击，检查是否到达对应内容 |
| 搜索是作品核心 | 明确赛道定位 | 作品确实利用搜索结果形成回答，搜索并非装饰按钮 |
| 使用元宝搜索 | 侦探赛道前三的明确资格条件 | 实际调用并能说明它在流程中的作用；调用证据是建议留存材料 |
| 避开时政话题、具体某个人的私事 | 原文明示选题边界 | 样例、功能定位和演示查询都遵守该边界 |
| 做进阶挑战则补对应证据 | 条件性提交要求 | 提交调查报告／真实触发提醒／截图查证录屏，与所宣称的能力对应 |

原文同时说明：用其他工具做的作品仍可争取本地前三、人气奖和 1024 超能大奖。**不能把“元宝搜索是赛道前三条件”扩大成“不用就完全不能参赛”**。优秀奖的工具资格是否同样限定，本文没有找到明确单独说明。

### 2.2 评委明确会看的方面

| 关注点【原文明确】 | 我的理解【推断】 | 建议准备的证据 |
|---|---|---|
| 查得准不准 | 回答与问题、对象、时间和证据匹配 | 用已人工复核的案例演示，保留原始查询和结果 |
| 来源点不点得开 | 用户能实际检查证据 | 演示中打开来源；别只展示一个来源名或无法访问的链接 |
| 好不好玩 | 交互有吸引力，价值容易体验 | 让首次使用者迅速完成任务；娱乐不是唯一可行形式 |
| 查不到敢不敢说不知道 | 不把缺失证据补成确定答案 | 准备查无可靠依据的额外测试，说明能力边界 |
| 难度：刁钻问题、多步调查、交叉验证 | 前三竞争中，需要呈现超出单次简单问答的能力 | 展示子问题、关键检索、独立来源以及结论形成过程 |
| 来源冲突时能否讲清判断 | 不是把矛盾结果都贴出来就结束 | 展示冲突内容、时间／适用条件差异和采信理由 |
| 有没有人真在用 | 前三竞争中，真实需求与使用证据重要 | 真实试用记录、反馈和修改；用户数量阈值未公布 |

原文明确说“不知道不扣分，瞎编才扣分”。这意味着诚实处理未知是核心质量，不应为了看似成功而编造结果。但这也不等于凡事回答“不知道”就满足“查得准”的目标。

## 3. 加分点如何转化成作品能力

**【原文明确】** 三类进阶功能会加分；前三还考察难度与真实使用。文章没有说界面特效、技术栈复杂、多 Agent 数量或报告字数本身加分。

**【建议】** 先保证一次查证完整，再选择最能服务目标用户的一项进阶能力。优先顺序是开发取舍建议，不是官方评分权重：

1. 用户能拿到有依据的结果，并点开对应来源。
2. 证据不足或冲突时，作品仍能给出诚实、可理解的反馈。
3. 在一个确实需要多步搜索的场景中展示难度。
4. 找到真实使用者，记录他们提出的问题、完成情况及反馈。
5. 在以上基础上扩展盯梢或截图入口，避免增加一个演示不完整的功能。

一个重要判断是：引用数量不等于交叉验证质量。多篇转载可能来自同一个原始消息；可点击链接也可能不支持旁边的说法。若要让“信得过”成立，应该检查来源是否独立、是否相关、是否真的支持结论。这是由赛道目标推导的质量要求，原文未规定最低来源数量。

## 4. 对赛道目的的猜测

以下均为根据文章措辞作出的推断，不是对主办方内部意图的事实断言。

**第一层：把 AI 幻觉问题转成可演示的产品能力。** 开篇花了篇幅解释自信胡说，结尾回到先查再说；评分又专门强调不知道不扣分。由此推断，主办方希望参与者展示“证据约束回答”的实际体验。

**第二层：让元宝搜索被真实接入，并产生场景案例。** 工具介绍、接入教程、免费额度、线上支持以及前三资格共同出现，支持“推动开发者采用、展示搜索能力”的推断。但不能进一步臆测商业合同或隐含评审偏好。

**第三层：鼓励有用户价值的作品。** 形式和题材开放，而前三明确关注真实使用。这意味着作品应能解释谁在什么时刻需要它，以及查到结果之后能做出什么更好的决定。

**第四层：降低入门门槛，同时保留拉开差距的空间。** 三步教程帮助初学者起步，进阶功能和复杂问题则区分更成熟的实现；不必把所有能力一次堆满。

## 5. 我对“侦探”的理解及容易走偏的地方

这里的侦探主要是**围绕公开信息解决不确定性**。正文明确避开具体个人私事，所以不能只根据名字把它理解成找人、追踪或隐私调查。

它的核心链条是：用户提出不确定的问题 → 作品理解要核查什么 → 搜索获取证据 → 判断证据是否足够、是否冲突 → 给出结论和来源 → 用户可自行核对。进阶能力延伸这条链条，而不是替代它。

“查得到”和“信得过”是两个不同问题：前者关乎能否找到相关信息，后者关乎这份信息是否足以支持判断。查到一段搜索摘要，不代表已经查清事实；找不到可靠证据，也不能直接推断命题为假。

“查最新”尤其要区分来源发表时间、描述事件发生时间和用户查询时间；“查模糊”要容纳多个候选；“查真假”要保留命题的适用条件。三类方向的共同结果结构可以相似，但判断方法不应完全相同。

对于黑客松成品，我认为最值得展示的是：**一个真实问题被解决的完整过程，以及在不能解决时如何准确地停下来。** 普通聊天框也能做到这一点，但若只是调用搜索后输出一大段没有逐项依据的文本，评委很难判断检索是否真正改善了答案。

## 6. 成品要求与验收清单

### 6.1 来自原文的最低交付包

- [ ] 能打开、能使用的作品，搜索处于核心。
- [ ] 3 次真实查询的截图或录屏，每次附结果和可点开的来源链接。
- [ ] 若争取侦探赛道前三，实际使用元宝搜索。
- [ ] 选题遵守时政和个人私事边界。
- [ ] 若宣称完成进阶能力，附与该能力对应的补充材料。

查证卡是原文给出的可选形式，不是唯一交付格式；网页、Skill、插件等也不必都提供。

### 6.2 建议的用户可见结果结构

| 字段 | 用途 | 依据性质 |
|---|---|---|
| 当前核查的问题／命题 | 避免答非所问，让用户知道查了什么 | 建议 |
| 答案或结论 | 先让用户读懂结果；真假类保留真／假／说不准 | 原文示例 |
| 简短理由 | 说明为什么得出该结论 | 原文提示词和图 05 |
| 关键说法对应的来源链接 | 让用户检查证据，而非只看一组参考网址 | 原文提示词 |
| 查询时间 | 避免把时效性结果当永久事实 | 查最新方向原文提出 |
| 来源日期、适用条件 | 辨别新旧信息和结论范围 | 建议 |
| 不确定之处／冲突说明 | 表达证据不足或不一致 | 未知与冲突是原文评审关注点；具体 UI 为建议 |
| 下一步可补充的线索 | 帮用户继续推进 | 建议 |

### 6.3 建议留存的演示证据

三次必交查询可围绕同一目标用户和场景，原文没有要求各覆盖一种查询方向。建议分别展示一个常规成功案例、一个需要多步或交叉验证的案例、一个具有实际使用价值的复杂案例，并逐项点开来源。

**另外补一条证据不足测试**，展示“不知道”的处理。这样既保留三次带结果和来源的正式材料，也验证原文特别重视的诚实边界。这个第四条是建议，不是官方新增数量要求。

若展示冲突处理，保存支持与反对的原文片段和日期；若展示持续提醒，保存变化前后内容及触发记录；若展示截图查证，保留截图输入、提取的待核查说法和最终查证结果。演示材料中标明真实查询时间，区分实时演示与历史记录。

真实使用证据建议包括：用户遇到的真实问题、是否完成任务、哪一步困惑、由此做过什么修改。不要把模拟用户、计划邀请或作者自测写成已有用户使用。

### 6.4 工程层面的建议，不是赛事强制条款

- 搜索失败、超时、无结果时有明确状态，不把接口异常表现成“该事实不存在”。
- 引用链接来自实际检索结果，避免让模型自行拼造。
- 评委的打开方式清楚；如需安装或账号，提供尽量短的说明。
- 可以保留检索请求、结果和回答的关联记录，便于排查与证明真实调用；不要把密钥暴露在演示中。
- 接口配额、模型和网络问题有可解释的降级；历史缓存展示应注明时间，不能冒充刚查到的信息。
