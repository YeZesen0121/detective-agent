## 实际实现

- migration `008_followups.sql`：持久追问队列、原幂等键/请求摘要、路由决定、引用、失败、研究关联、活动时间、epoch，以及 run 绑定的原问题/基线。
- `FollowupHost` 每次最多两个活动路由任务；每个任务120秒、最多2次模型和累计2000输出token，并受原同案/访问组/全局交互预算。仅允许 `purpose=followup`，禁 search/read/checkpoint/events 写入。供应商异常立即 Abort，即使业务捕获异常再调用也拒绝。
- 追问与伴读复用 `experience_scopes` 同一个交互池，领取互斥、共享epoch；不是每个追问新建免费额度。读报告/历史不触发生成。
- `research_same_scope` 重新核对最新版本、活动任务、剩余研究预算；事务创建 trigger=followup 的普通 run，继承原窗口和材料。I 接收原 question、baseline、checkpoint。
- `explain` 只消费绑定版本；P校验 claim/evidence ID，语义仍由 I 判断。新案只是建议，不能自动创建。
- `needs_budget_confirmation` 不创建新窗口。显式 `add_budget + followupTurnId` 原子校验该追问后建新窗口；相同幂等键重放不再加额度。
- 取消/中断后的 resume 保留原追问/基线/剩余窗口；普通 add_budget 继承追问时绑定最新版本。旧版补查与旧版预算确认返回 STALE_VERSION；stale run 不从旧材料发布新partial。
- 启动/关闭持久化 SERVER_RESTART、提高epoch，等待中的路由不会重跑。已发送unknown保留预约；恢复不退为未发送。

## W 可用接口

公共真源：`src/shared/followup-http.ts`、`src/shared/runtime-http.ts`，均有原有API envelope。

|操作|请求与结果|
|---|---|
|POST `/api/v1/investigations/:id/followups`|Idempotency-Key；body `{resultVersionId,question}`；202 `{followupTurnId}`。无Origin/无归属/已有活动任务按既有门禁拒绝。|
|GET `/api/v1/followups/:id`|FollowupView：queued/running/completed/failed；路由完成前turn=null；完成后turn含route、answer、claimIds、newRunId；另有evidenceIds/researchPurpose/suggestedQuestion/error/latestResultVersionId。|
|GET `/api/v1/investigations/:id/followups?after=0`|每页最多50个view，nextAfter=null结束；已知进行中id单独轮询。|
|GET `/api/v1/investigations/:id/followups/submission`|携原Idempotency-Key，返回 `{submission:null或{followupTurnId}}`；只读恢复丢响应，null不等于允许自动重发POST。|
|POST `/api/v1/investigations/:id/runs`|原StartRun增可选followupTurnId；仅action=add_budget允许。必须用户明确点击追加，携当前previousRunId和原追问id；返回原StartedRun。|

`turn.newRunId`为稳定的关联补查run；view的activeRunId当前为该关联run的兼容字段，**不可据此推断run仍在运行**，统一GET run确认状态。展示研究方向不等于调查已完成，新版本必须显式打开。不同逻辑动作使用不同幂等键，同一动作不能因刷新或网络失败更换键。

配置门：`InvestigationRuntimeOptions.enableFollowups === true` 才接收生成请求。当前正式truth profile不打开；I N3还是占位时不得宣称可用。关闭生成后历史GET仍可读。
