# 队友 Codex：技能、工具与开工检查清单

版本 v0.1｜2026-10-24｜供自己的多个对话或队友 Codex 使用。

本文件初次产出时只做文档；当前用户已指示开发，G0已发布。接任务优先使用[第一批实际派发](13-现在开始并行开发.md)，其中有真实SHA和模块范围。下面通用提示词作为准备参考，不要求队友重复建立G0或抢总集成角色；本清单不代表队友机器已经配置。

## 1. 下一步的顺序

1. **先保留一个主对话负责总集成 P。** 复核实施设计、接口契约与任务包是否一致，记录需要修正的技术细节；不重问 PRD 已确认的需求。需要用户决定的产品变化才单独提出。
2. **开始编码后，先做 T02a 公共底座，同时准备 T01 外部接口探针。** P 建立唯一仓库、锁定依赖、公共类型、样例、最小 HTTP 外壳和验证命令。T01 的真实调用须有对应凭据与预算；没有凭据先准备探针，不能把替身成功算成真实 API 可用。
3. **T02a 验证通过并发布基准 SHA 后，再派发模块。** I 做调查引擎，W 做前端，E 做截图/伴读/语音；P 继续 T02b 平台和早期部署，之后承担 M 盯梢或另派。角色可以由自己的不同对话承担，无需等队友。
4. **先贯通一条真实用户路径，再补齐全部核心需求。** G1 是输入→真实调查→结果→来源；之后完成截图、伴读、语音、后台盯梢及异常恢复，最后按验收矩阵收集证据。

T02a 放行只表示公共接口可用于受控开发，**不表示平台完整、真实接口可用或产品通过验收**。具体任务与依赖见[并行开发任务包](../并行开发任务包.md)，验收见[验收追踪矩阵](../验收追踪矩阵.md)。

## 3. 最小工具清单

“必需”指完成对应工作的能力；同一能力不需要同时安装多个工具。

|层级|工具或能力|谁需要|就绪的证据|
|---|---|---|---|
|必需|可正常使用的 Codex；能读写该工作目录、执行命令、查看结果|所有开发者|能读项目文档，在获准的测试位置写入并读取一个临时文件，运行版本检查|
|必需|Git；同一个项目仓库的读取和提交协作方式|所有开发者|`git --version`；进入已发布仓库后能读取实际 HEAD 和工作区状态|
|必需|与 G0 一致的 Node.js 和 npm|所有开发者|版本一致；G0 发布后在自己的 checkout 中 `npm ci` 成功|
|必需|可访问包源、相关官方文档和自己负责的 API|按角色|记录实际访问结果；文档能打开不等于鉴权请求成功|
|必需|普通浏览器|W、P；其他角色建议有|能打开本地或测试环境，实际操作自己负责的流程|
|项目依赖|TypeScript、Vite、Fastify、Zod、better-sqlite3、Vitest、Playwright|由 P 在仓库锁定，大家按锁文件安装|不在个人电脑上分别全局安装不同版本；实际以 G0 的 package.json 和锁文件为准|
|浏览器测试|Playwright Test 及匹配的浏览器二进制|W、P、验收执行者|项目测试可启动浏览器并产生测试结果/失败 trace|
|建议|ripgrep（`rg`）|所有开发者|`rg --version`；缺失时可用原生命令查找，不阻塞开发|
|二选一或不用|GitHub 连接器、GitHub CLI `gh`，或人工通过网页处理 PR|P；队友按协作方式|能访问指定仓库；Git 是本地版本工具，连接器/gh 是协作便利工具|
|按需|Python 3|使用 ui-ux-pro-max 搜索脚本的 W/设计对话|Python 可运行且技能搜索返回结果；不是整个产品后端的要求|
|按需|Docker 或目标平台提供的构建/部署环境|P/部署负责人|按最终部署方案验证构建、持久卷和恢复；不要求每位队友安装 Docker|
|按需|Git Bash 或 WSL|运行确实依赖 Bash 的技能脚本者|先检查脚本和路径兼容性；不为了普通 TypeScript 开发强制迁移到 WSL|

Node 已在 G0 阶段统一选择 **24 LTS，确切版本24.19.0**，与主机环境一致；取代原草案的22候选。依赖声明允许24，SQLite读写已验证，完整基线结果以G0报告为准。队友跟随 `.node-version` 和锁文件，不各自升级。[Node 官方版本说明](https://nodejs.org/en/about/previous-releases)

G0干净安装补充：要求npm11.17+，推荐固定11.17.0。仓库已记录精确包脚本策略：SQLite使用包内预编译文件，避免不必要的本机C++编译；esbuild安装脚本保留。不要自行删除该策略或改成全局ignore-scripts。具体失败和修复证据见[并行基线记录](../runtime/并行基线发布记录.md)。

Playwright 的 npm 包与浏览器环境均需准备。G0 安装依赖后，使用项目内已锁定的 Playwright CLI 安装所需浏览器；不要在项目未配置时直接运行 `@latest` 初始化另一个工程。CI/Linux 环境还需核对系统依赖。[Playwright 安装说明](https://playwright.dev/docs/intro)

Windows 可以直接使用 PowerShell。遇到 `npm.ps1` 执行策略问题可使用 `npm.cmd` / `npx.cmd`，不应为此盲目修改整机执行策略。原生依赖若安装失败，先记录 Node 版本、架构和错误，确认预编译包可用性，再决定是否补编译工具。[Codex Windows 文档](https://learn.chatgpt.com/docs/windows/windows-sandbox)

## 4. Skills：公共最小集与角色增配

Skill 提供工作方法，不提供 Git、浏览器或供应商账户。以下是本项目的推荐配置，不是 Codex 或项目运行的硬依赖。暂时缺 Skill 时，也必须执行任务包规定的测试、审查和交付要求。

### 4.1 建议每位开发者配置的公共最小集

|Skill|在本项目何时使用|要求与边界|
|---|---|---|
|`verification-before-completion`|每次声称已修复、通过或可交付之前|写明实际命令、结果和未验证项；静态检查不能替代真实调用或运行测试|
|`systematic-debugging`|安装、构建、测试、接口或运行失败时|先找可复现原因，再改代码；辅助脚本可能需要 Bash，不影响先按文档做根因分析|
|`test-driven-development`|状态机、预算、幂等、隔离、数据快照等关键行为|先建立能暴露问题的失败用例；不机械地为文案和低风险排版写无意义测试|
|`receiving-code-review`|处理总集成或队友的审查意见时|核实意见及影响后修改；报告不采纳的理由和证据|

本机安装登记将以上四项来源标为 [obra/superpowers](https://github.com/obra/superpowers)。这是来源定位，不代表远端最新版与本机内容完全一致；队伍应固定所采用的版本，并保留许可证。

### 4.2 按模块增加

|Skill|建议角色|使用目的|额外条件|
|---|---|---|---|
|`ui-ux-pro-max`|W、独立 UI 设计对话|加载/取消反馈、错误恢复、触控、阅读层级、语音播放交互|需要完整 `data/`、`references/`、`scripts/` 和 Python；遵守[UI 独立协作边界](10-UI独立协作边界.md)，不要另造一套视觉稿|
|`playwright-best-practices`|W、P/验收|稳定定位、等待、隔离、失败 trace、端到端测试|Skill 与 Playwright 执行器需分别验证；来源登记为 [Currents](https://github.com/currents-dev/playwright-best-practices-skill)|
|`vercel-react-best-practices`|W|React 状态、渲染和请求性能|本项目是 React/Vite；只采用适用建议，不照搬 Next.js 专属规则；来源登记为 [Vercel](https://github.com/vercel-labs/agent-skills)|
|`using-git-worktrees`|P、同机多对话的目录管理者|隔离 checkout，避免不同对话互相切分支、覆盖文件|Git 能力才是必需；技能中的 Bash 示例应适配实际 shell|
|`security-best-practices`|P、I；E 按需|会话隔离、上传、密钥、URL 读取和服务端边界|按 TypeScript 与实际组件选择参考，不扩大成无关系统重构；来源登记为 [OpenAI Skills](https://github.com/openai/skills)|

角色简配：**I = 公共集；E = 公共集；W = 公共集 + UI/React/Playwright；P = 公共集 + worktrees/Playwright/security。** I/E 触及 URL、会话、上传等边界时增加对应安全参考。M 若单独派发，使用公共集和平台恢复测试要求。

### 4.3 不列为人人必装的技能

- `executing-plans`：本机版本会调用自身脚本以及 `subagent-driven-development` 的工作区、审查包脚本，并引用 TDD、worktrees、review、finishing 等技能。不是复制单个文件就能运行。确需采用整套流程时，先验证完整依赖和 shell；本项目默认可直接按任务包逐项执行。
- `requesting-code-review`：本机版本要求派发审查子 Agent。仅在当前宿主支持且任务授权允许时采用；否则将同样的审查材料交给独立人工/对话审查，不伪称子 Agent 已审过。
- `brainstorming`、`grill-me`、`writing-plans`：适用于需求或方案仍有实质空白的阶段。每个实施对话不必重新开启一轮产品需求讨论；发现真实冲突时回到 P 处理。
- FastAPI、Postgres、Supabase、shadcn 等技能不属于当前选定栈的公共必备；未采用对应技术就不用安装。
- 不要求额外安装多 Agent 调度框架、向量数据库或浏览器 MCP。现有多对话 + Git + 项目测试已经能支撑本轮协作。

## 5. 如何安装和转交，避免“装了但不能用”

优先由 P 选定完整技能目录和版本，记录来源、版本/commit 或内容校验值、必要的本地修改与依赖。队友从同一审核版本安装；也可让内置 `skill-installer` 按明确仓库路径安装并核验。不要让每位队友独立搜索同名技能后随意挑一个。

Codex 支持用户级 `~/.agents/skills/<技能名>/` 与仓库级 `.agents/skills/<技能名>/`。Windows 用户级通常为 `%USERPROFILE%\.agents\skills`。技能目录应包含 `SKILL.md` 及其需要的脚本和参考；安装后检查能否被发现，未刷新时重启。避免全局与项目内出现同名但不同内容的副本。[Codex Skills 官方说明](https://learn.chatgpt.com/docs/build-skills)

本次静态检查发现：

- 推荐表中 11 个技能目录在主机存在，但这不证明队友已安装、加载或成功运行。当前没有制作或分发技能安装包。
- `ui-ux-pro-max` 本机说明含 `C:/Users/111/...` 个人路径。转交时按队友实际技能目录修正，完整保留其数据和脚本；本机 lock 登记未提供该技能来源，不能凭名字宣称它等同某个远端版本。
- 本机其他推荐技能大多有安装来源登记，但登记不等于完整依赖已通过验证。带 Bash 脚本的流程技能需另外检查。
- Windows Junction/符号链接可能指向主机私有路径；转交需核实实际目标，不能仅发送失效链接。不要复制整个个人 `.codex` 目录、账户文件或历史会话。

完成安装要分三层记录：**文件完整 → Codex 能发现并读取 → 在实际任务中成功执行**。只通过第一层，就只写“文件就绪”。

UI 搜索的无付费验证例子（先进入实际技能目录）：

```powershell
python .\scripts\search.py "loading cancel progress feedback" --domain ux
```

若 `python` 不可用，先确认 `py -3` 或实际解释器路径。记录所用命令和结果，不能把“读过 Skill”写成“运行过搜索”。

## 6. API、账户与付费边界

|用途|由谁配置|何时需要|
|---|---|---|
|Codex 的开发模型访问|每位使用者自己的可用配置|开发对话开始前；与产品 API 无关|
|元宝搜索服务|I/P 的服务端测试环境|T01 与真实调查闭环；按 API 核查选择正确鉴权方式|
|模型、视觉、网页读取|I/E/P，按职责分配|各自真实探针和集成；不得用 Codex 登录态冒充产品模型凭据|
|腾讯 TTS|E/P 的服务端测试环境|真实语音合成与听音验收|
|部署平台、运行环境与持久存储|P|T08 早期部署和恢复验证|

前端 W 在契约开发阶段通常不需要拿到上述服务端 Key。其他角色也只配置自己的必要凭据。凭据通过本机环境或平台秘密配置提供；报告中只写变量名、是否就绪、脱敏错误，不粘贴值。

[Toklens 核查记录](05-Toklens算力核查.md) 是特定开发算力候选的历史核查，不是所有队友的必选项，也不等于产品供应商接口已接通。按实际账户另验，不依赖旧价格或余额。

## 7. 队友首次进入项目的检查清单

- [ ] 获得文档；明确自己是 I/E/W/P/M 中哪个角色、领哪个 DEV-T 任务。
- [ ] 记录操作系统、shell、Git、Node/npm 版本；不要写成“环境应该没问题”。
- [ ] 明确仓库地址、基准 SHA、自己的分支和独立工作目录；G0 尚未发布则标“等待基线”。
- [ ] 读取任务对应的契约、fixtures、写入范围；不修改他人所有的公共文件。
- [ ] 仅安装/验证本角色所需技能和工具；安装修改需有相应任务授权。
- [ ] G0 发布后，在本机执行 `npm ci` 和任务要求的基线检查。现阶段没有 package.json，不应执行这些命令并把失败算作产品缺陷。
- [ ] 对真实 API 标明“未配置 / 已配置未验证 / 真实调用通过 / 失败”，替身结果独立标记。
- [ ] 返回准备报告：可开始项、阻塞项、实际证据、下一动作。不能因为缺真实 Key 就停掉所有可独立进行的契约工作。

无需产品代码的版本检查：

```powershell
git --version
node --version
npm.cmd --version
```

仓库已发布并进入正确 checkout 后，再检查：

```powershell
git status --short
git rev-parse HEAD
```

准备报告应注明检查的机器与时间；主机通过不代表队友机器通过。
