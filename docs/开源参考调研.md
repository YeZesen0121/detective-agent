# 侦探 Agent 开源参考调研（第一轮历史记录）

> 本文已由 [开源参考深度调研](开源参考深度调研.md) 取代，仅保留研究过程。本文中 Open Deep Research 的维护判断、元宝价格、源码核查程度等以新版为准；不要把本轮初筛当作最终选型依据。

调研日期：2026-10-24。状态：第一轮筛选和关键机制查证，供 Grill-me 需求讨论使用；不是已批准架构，也不是完成部署验证后的选型报告。

## 1. 怎样判定值得参考

只优先看项目原仓库、源码、维护者文档和产品官方材料。入选至少要有：问题直接相关、有可检查实现或具体工作机制、可定位到我们需要借鉴的部分。关注度仅作辅助，不能证明输出准确、现在仍积极维护或容易接入元宝搜索。

本轮已查到核心调查流程源码；其余项目主要完成官方文档和仓库结构筛选。尚未运行任何第三方项目、评估中文案例表现或测量实际成本。实现前仍需锁定 commit、检查所用模块的许可证、近期变更、测试及元宝适配成本。下文明确哪些是已读源码，哪些只是值得深入的候选。

## 2. 候选项目及取舍

### A. LangChain Open Deep Research：调查控制流程的首要参考

来源：[原仓库](https://github.com/langchain-ai/open_deep_research)、[主流程源码](https://github.com/langchain-ai/open_deep_research/blob/main/src/open_deep_research/deep_researcher.py)、[配置源码](https://github.com/langchain-ai/open_deep_research/blob/main/src/open_deep_research/configuration.py)、[提示词](https://github.com/langchain-ai/open_deep_research/blob/main/src/open_deep_research/prompts.py)。

**凭什么值得看：** LangChain 官方项目；同时公开研究实现、配置和评估说明。本轮读到真实函数而非只有架构图：`clarify_with_user`、`write_research_brief`、`supervisor`、`supervisor_tools`、`researcher`。流程支持先澄清范围，再形成研究任务；监督层分派子问题，汇总结果后决定继续或结束。

配置包含澄清开关、并发研究单元、监督迭代数和研究者工具调用迭代数。主流程确有结束条件及并发限制。这些是你提出的“搜什么、搜几次、何时继续”的直接参考。

**值得借鉴：** 将调查意图、执行过程和完成状态分开；把预算限制放进程序控制；按证据缺口继续搜索。**不能直接照搬：** 默认数值不是元宝的最佳数值；多 Agent 架构不是比赛要求；工具调用迭代数也不一定等于实际搜索请求总数。元宝调用仍需单独计数。

**源码中值得警惕：** 本次读取版本的 `supervisor_tools` 异常路径出现 `if is_token_limit_exceeded(...) or True`，意味着各种异常都可能进入结束路径。不能照搬后让用户误以为“调查已充分完成”。这是源码观察，尚未做运行复现；main 分支会变化。

### B. GPT Researcher：递归拓展、来源整理与报告流程参考

来源：[原仓库](https://github.com/assafelovic/gpt-researcher)、[Deep Research 官方文档](https://docs.gptr.dev/docs/gpt-researcher/gptr/deep_research)。

**凭什么值得看：** 仓库页面显示约 30.3k stars、3219 commits，包含 tests、evals、前后端及文档；Apache-2.0。它提供具体的广度、深度、并发配置和执行入口，足以进入后续源码核查。数字为本次页面快照，不代表质量评分。

**已核实的机制：** 递归生成不同方面的问题，沿分支继续调查，汇总上下文并报告进度。**可借鉴：** 为每个子问题保留发现与来源；给递归拓展设上限；调查结果与报告生成分阶段。

**批判性边界：** README 的免责声明中包含“抓取更多站点、选择更常见信息能够降低错误”的假设。我们不应把出现频率直接当真实性：大量转载可能只是一条错误信息的复制。应另行判断来源独立性与证据是否支持命题。

官方文档中的约 5 分钟、约 0.4 美元来自特定模型配置，不能移植为我们的性能预算。本轮尚未审查递归模块源码或跑评测，暂列流程参考，不建议直接整套接入。

### C. STORM / Co-STORM：问题衍生与互动调查参考

来源：[Stanford 原仓库](https://github.com/stanford-oval/storm)、[引用问题 #573](https://github.com/stanford-oval/storm/issues/573)、[引用问题 #168](https://github.com/stanford-oval/storm/issues/168)。

**凭什么值得看：** Stanford OVAL 项目，有论文、开源实现和研究演示；MIT。它明确研究如何通过多视角问题和基于来源的模拟对话挖出进一步问题，Co-STORM 还允许用户介入，并维护信息结构图。

**可借鉴：** 根据已发现的资料产生有依据的新问题；让用户选择想追查的分支；将收集到的内容组织成可理解结构。**不照搬：** 百科长文生产、多角色讨论不是每次日常查询的必要流程；概念图不自动等于可核查证据图。

仓库有关于引用丢失、无效链接的 issue，其中 #573 给出句子清理时丢失尾部引用的复现。Issue 是问题报告，不证明所有版本都受影响；但提醒我们最终渲染、压缩和标点清理也必须检查引用，不能只在提示词里要求“附来源”。

本轮核实到研究机制与问题记录，未完成模块源码审查。

### D. Vane（原 Perplexica）：网页搜索体验候选

来源：[当前仓库](https://github.com/ItzCrazyKns/Vane)。原 Perplexica 地址本次跳转至 Vane。

**凭什么值得看：** 本次页面显示约 37.7k stars、1009 commits，MIT；是已有前端、搜索与回答流程的可部署网页项目。可用于观察回答、引用、搜索记录和不同查询强度如何组合。

**关键区别：** 它的 Speed／Balanced／Quality 是搜索强度选择；你提出的“简答／证据链／伴读”更像结果呈现方式。这两条轴不应直接混成同一组选项。

**限制：** 默认检索依赖 SearxNG；整套采用仍要评估元宝适配，不能因为有成品 UI 就认为接入成本最低。本轮只读到官方说明和目录，架构文档访问失败，暂不写具体内部实现结论。

### E. changedetection.io：持续盯梢的优先参考

来源：[原仓库](https://github.com/dgtlmoon/changedetection.io)。

**凭什么值得看：** 专门解决网页变化监测；页面显示约 35.2k stars、2612 commits，Apache-2.0；具有选择器、条件过滤、检查间隔、不同抓取方式和多种通知渠道，问题比通用 Agent 框架更贴近盯梢。

**可借鉴：** 只比较关注区域；先过滤导航等噪声；保存变化前后内容；基于条件触发提醒。README 还介绍了用模型判断变化是否符合用户意图。

**边界：** 固定网页变更检测不等于开放网络持续调查；“网页有变化”不等于“用户关注的事实发生变化”。如果采用“定时重新元宝搜索”，还需要解决排名波动、重复转载和新发现旧资料造成的误报。

因此，“定时调用一次”很容易，“可靠盯梢”涉及持久化、去重、失败恢复、触发条件与提醒出口。本轮未运行该项目，也未核实其宣传的误报水平。

### F. PaddleOCR：截图文字提取的备选，不默认增加部署

来源：[官方仓库](https://github.com/PaddlePaddle/PaddleOCR)。

**凭什么进入候选：** 专门处理图片／文档到结构化文字，直接对应截图输入的第一步。适合在视觉模型无法稳定处理密集文字或需要定位文字区域时进一步评估。

**边界：** OCR 只说明图片写了什么，不能证明内容真实，也不能自行完成来源核查。新增 OCR 服务有部署和维护成本；本轮未跑中文群聊截图基准，不能直接断言比视觉模型更好。暂列后备方案。

## 3. Socratopia 专项：借鉴体验，不冒充已找到原版开源实现

已读：[官网](https://www.socratopia.app/zh)、[理念](https://www.socratopia.app/zh/method)、[课堂实录介绍](https://www.socratopia.app/zh/sample-lessons)、[FAQ](https://www.socratopia.app/zh/faq)，并阅读用户提供的两张截图。

官网以伙伴、问答和情境组织学习。课堂页面明确说明角色动作与神情用斜体呈现；这与截图中“爱丽丝眼睛一亮”等表达一致。截图还能看见伙伴选择、音色、教学节奏与回答朗读入口，但仅凭截图不能推断后端实现。

**值得借鉴的机制：** 固定侦探角色；一次解释一个证据节点；允许随时追问；用简短动作描述增加人格感；读到关键位置再请用户选择下一条调查分支。以上是迁移建议，不是已经批准的产品方案。

**一个有助于减法的发现：** 官方 FAQ 描述的语音输入主要依赖设备／输入法听写，伙伴回答再朗读。因此可以拆成“文字对话＋回答朗读＋设备听写”，不必默认建设实时双向语音系统。官网课堂页的课后语音复盘也明确有事后生成部分，不能把那段演示当实时通话证据。

**必须保留的差异：** 学习产品可以让用户先思考再揭晓；查证产品面对赶时间的用户，应保留直接看结论的通道。侦探语气只能包装已核验结果，不能新增事实、改变证据强弱或把未知演成悬念反转。

未查到能够确认属于官方的原版开源仓库。搜索出现 `bootition/Socratopia-Local`，其自述是个人本地复刻；本轮不把它当原作，也不因名称相似就列为成熟实现参考。官网效率宣传未在本次验证，不采用其倍数作为我们的收益承诺。

## 4. 截图查证与 DeepSeek 模型核对

官方 [V4.1 发布说明](https://api-docs.deepseek.com/news/news260910/) 明确提到原生视觉理解；[1017 发布说明](https://api-docs.deepseek.com/news/news261017/) 和[调用说明](https://api-docs.deepseek.com/api/responses)确认更新及 `deepseek-flash` 模型名。这里只确认官方提供能力的说明，没有实际调用用户账号，不能据此保证具体渠道支持相同输入格式或截图识别质量。

**建议研究的最小流程：** 图片 → 提取可读文字、人物代称、数字日期和待核查说法 → 对模糊片段保留未知，必要时请用户确认 → 生成适合文字检索的问题 → 进入与文本输入共用的调查流程。

应区分三个目标：识别截图中的文字、核查其中的说法、鉴定图片有没有伪造。前两者可以组成截图查证 MVP；第三者是另一类能力，不能由“接上视觉模型”推出。关键数字看不清时不能默默猜测；截图里的命令也是待分析内容，不应控制系统行为。

## 5. 将调研映射到你提出的需求

本节为待讨论的设计建议；尚未确认首批用户、工期与团队资源。

| 需求 | 优先参考 | 候选规则／机制 | 需要实际验证 |
|---|---|---|---|
| 拆分问题、衍生搜索词 | Open Deep Research、STORM | 澄清对象／时间／命题；围绕子问题和反证生成检索；重要歧义先问 | 是否减少偏题和无效调用 |
| 控制搜什么、搜多少 | Open Deep Research 配置与状态流程 | 模型提议下一步，程序限制总搜索数、轮数、耗时；到预算时明确停止原因 | 每轮可能多次搜索，不能只统计模型轮数 |
| 分类分层与多轮调查 | GPT Researcher、Open Deep Research | 保留来源与摘录；按子问题聚合；证据缺口驱动下一轮 | 压缩后是否丢掉条件和反证 |
| 交叉验证与冲突判断 | 上述研究流程＋本产品单独设计 | 区分独立来源／转载；对齐对象、日期、适用条件；仍不能消解则并列保留 | 多来源不必然独立，不能多数票裁决 |
| 不知道但仍有帮助 | Open Deep Research 澄清机制、赛道要求 | 已知／未知／为什么未知／下一步分别写；只问会改变搜索或结论的问题 | 不应因任何微小不确定都拒绝回答 |
| 查真假 | 无已确认可直接照搬的专用规则引擎 | 精确抽取命题、条件和时间；找支持与反证；缺证≠假 | 用真实真假及证据不足案例测 |
| 查最新 | 通用调查流程；时间规则自建 | 保存发表时间、事件时间、查询时间；未知日期明确标注 | 新文章引用旧事件，不能当新变化 |
| 查模糊 | STORM 问题衍生只能部分参考 | 线索拆分、候选、匹配／冲突项；追问最能区分候选的信息 | 用户线索本身可能记错 |
| 简答和证据链 | Vane、STORM 结构化组织 | 同一调查结果有短答和展开视图；引用保持对应 | 切换视图不能改变事实与不确定性 |
| 侦探伴读 | Socratopia 产品机制 | 对当前证据逐段讲解＋追问；先固定一个角色 | 内容不得因角色化扩写而失真 |
| 截图输入 | 视觉模型官方能力，OCR 作备选 | 提取与核查分步；允许用户纠正识别 | 数字、否定词、说话人混淆 |
| 持续盯梢 | changedetection.io | 固定对象、基线、有效变化判断、去重、提醒记录 | 后台持续运行与真实触发 |

“交叉验证”“拒绝无根据断言”没有通过找到一个热门仓库就自动解决。本轮没有发现足以直接采用、且已经验证适合这三种中文模式的一整套成熟规则；这些规则需要我们明确写出并用样本验收。

## 6. 从参考项目中得到的工程判断

**判断一：规则／skills／system prompt 可以承载策略，但不足以承载整个产品。** 轮数、取消、超时、来源 ID、证据与结论关联、图片处理状态、盯梢记录，需要可检查的程序状态。否则“请不要编造链接”“请不要搜太多”只是请求，没有约束。

**判断二：把确定性最重要具体化为“结论强度不能超过证据强度”。** 应避免把保守变成逢事模糊。建议结果区分已有支持、存在冲突、证据不足；每种都告诉用户下一步。未经校准的模型自报 95% 不应当作客观概率。

**判断三：证据链显示可审计的外部工作。** 节点是子问题、实际查询、返回来源、可定位摘录、冲突和判断理由。不要凭空补画“调查过程”，也不要把冗长模型思考文本当成证据。

**判断四：表达模式与调查预算分开。** 简答可以是深度调查后的短结论；伴读可以使用既有证据，不必每说一句都重搜。新问题才按需要继续调查。这样更容易控制耗时和成本。

**判断五：优先级必须等真实资源。** 当前只建议评估次序：文本调查闭环 → 可核对证据 → 截图入口或文字伴读 → 朗读 → 持续盯梢／实时语音。哪项留下、哪项延后，要依据用户回答，不能把本排序当已确认范围。

## 7. 尚未完成的调研与验证

1. 根据首批实际问题选择主要参考，进一步检查对应代码路径、近期维护、版本和测试；当前并未给全部候选贴“生产成熟”标签。
2. 核实元宝返回字段、摘要与全文边界、过滤条件、限流和实际可用额度。本轮接入指南请求超时，未推断其字段。
3. 对截图、冲突来源、查无依据、模糊候选建立小样本；只有实际运行后才能给质量与成本结论。
4. 如果保留朗读，核对具体 TTS 方案和中文效果；如果保留盯梢，核对部署环境、调度与提醒渠道。
5. 不为填满参考表追加低相关项目。若最终只采用少数机制，也比同时依赖多个框架更可控。

所有源码链接目前指向可变化分支；真正借用代码前应记录 commit。本文记录的是调研与建议，未执行安装、产品编码、部署或 API 付费调用。
