# Hermes UI 收敛与迁移协作说明

版本：v2 · 2026-10-24。对象：叶泽森、队友及正在制作 UI 的 Hermes。

**v2 入口：** 先读 [README-先读.md](README-先读.md)，按 [01-发给Hermes.txt](01-发给Hermes.txt) 开始。最终返回 Codex 的产物及验收标准以 [03-最终交付给Codex.md](03-最终交付给Codex.md) 为准。本版在原研究方案上补齐“直接接收 ZIP → 分轮 grill-me → 交回成果包”的闭环。

**建议路径：通过 UU 回到队友原来的 Hermes 设计会话，以现有可操作网页为基准，先保存成果，再澄清偏好、局部调整、扩展页面，最后用新环境实际接手验证迁移。**

本文是研究后形成的协作建议与接收任务，不是已确认的视觉规范。用户已说明现有产物是可打开、可操作的网页或前端项目；尚未检查队友机器、原会话、版本、源码及实际引用资料，不能断定效果来自某个技能或记忆。

## 1. 你现在怎样用这份文件

1. 优先在原 Hermes 会话上传 `Hermes-UI协作包-v2-2026-10-24.zip`，让它检查附件并解压到新目录。若入口不接收附件或工具访问不到文件，再通过 UU 将 ZIP 放在队友电脑，提供实际路径。UU 用来操作这台机器；资料交接以 Hermes 实际读到的文件为准。
2. 让队友定位原来产生满意设计的 Hermes 会话和项目目录。远程操作时由一人输入，等当前生成结束再交接控制，避免两人同时修改。
3. 在原会话粘贴 [01-发给Hermes.txt](01-发给Hermes.txt)，附上本文件，或提供它在队友机器上的实际绝对路径。不要把你电脑的 `D:\侦探agent` 当成队友也有的路径。
4. Hermes 第一轮只核对资料、保存基准、提出当前最值得问的 1–3 个问题。你先指出满意页面中喜欢的区域和最想解决的问题，无需先学设计术语。
5. 一轮完成一处关键调整或一个流程片段，看到前后对比后再决定下一轮。每轮保存确认记录；不要等全部页面画完才整理交接。

**不必先迁移到你自己的 Hermes，也不必为了安装技能重开原会话。** 技能安装遇到兼容问题时，先让原会话直接读取包内完整 `SKILL.md`，按协议提问；这算临时加载文件，不算安装验证通过。

## 2. 三条路线及取舍

|路线|优点|代价与边界|本项目选择|
|---|---|---|---|
|在队友原会话继续，并逐轮形成交接包|直接利用现有成果与可用上下文|需要远程配合；仍需把关键知识写成文件|现在采用|
|立即把成果和上下文搬到自己的 Hermes|后续可独立操作|尚未弄清依赖和偏好，容易把问题变成环境排查|基准和规则稳定后做小规模验证|
|只把需求和截图发给新 Agent 重做|启动材料少|丢失源码、素材、交互和决策细节，增加风格漂移|仅在源码无法取得时作为降级方案|

这三条路线的取舍是针对本项目的建议，不是外部资料证明的效果排名。不能保证另一模型重新生成的页面完全相同；能做的是保存已有实现、明确可变部分，并用实际产物检查延续性。

## 3. 成熟方法分别解决什么

|问题|可借鉴的方法|本项目怎样落地|依据|
|如何规范化|设计评审围绕目标、范围和具体反馈开展|每轮只明确目标、变更范围、结果和确认状态|[NN/g：Design Critiques](https://www.nngroup.com/articles/design-critiques/)|
|怎样使反馈真正影响下一版|评审后回顾，连接反馈与前后变化|每个修改关联用户原话；记录采纳、暂缓与原因|[NN/g：Closing the Loop](https://www.nngroup.com/articles/after-design-critique/)|
|怎样使多个页面一致|共享设计变量与组件状态|从当前源码提取颜色、字体、间距和组件，新增页面复用它们|[DTCG 2025.10](https://www.designtokens.org/tr/2025.10/format/)、[Storybook 官方说明](https://storybook.js.org/docs/get-started/why-storybook)|

外部资料支撑上述方法，不直接提供本项目的一整套现成流程。下文的阶段、文件结构、对照实验和迁移门槛是结合项目情况设计的执行方案。DTCG 是社区组发布的交换格式规范，并非 W3C 正式标准；当前无需为此引入专门工具。Storybook 也只是可选实现，少量页面用现有预览入口展示状态即可。

## 4. 第一步：锁定现有成果与实际上下文

Hermes 先检查当前项目与这次设计有关的可访问资料，输出一张清单。只检查有关文件；不要遍历或导出队友其他私人项目。

|检查项|要留下的内容|用途|
|满意版本|页面入口、源码位置、截图、日期；用户确认是否正是满意的那一版|避免误改另一个分支或版本|
|代码基准|Git 分支、完整 SHA、未提交文件；若没有 Git，保存源码快照和文件校验值|能够找回起点|
|打开方式|运行时版本、包管理器、锁文件、安装/启动命令；单文件网页则记录打开方式|换机器可以打开|
|视觉依赖|字体及回退字体、图片、图标、样式、组件；远程 URL 与本地路径分开列出|发现离线或换机后会变化的因素|
|工作上下文|Hermes 版本、当前会话标识、实际工作目录、模型名称和可见设置|后续诊断差异；不导出密钥|
|项目指令与技能|实际读取的项目规则、技能原文/版本/路径、模板和引用文件|区分“已安装”和“本次确实用过”|
|设计过程|关键用户反馈、采用/拒绝的方案、对应产物版本|理解为什么保留或放弃某种做法|

建立 `baseline-v0` 的可恢复副本。SHA 不能覆盖未提交修改，所以未提交源码也要保存在快照中；保留锁文件和必要素材，不打包 `node_modules`、凭据、会话数据库、音频、私人上传。若保存失败，明确说明，先继续只读评审。

资料与效果的关系必须分类记录：

- **已证实使用**：有本次会话工具记录、引用或文件变更证据。
- **存在但未证实使用**：找到了技能/参考文件，无法确认本轮加载过。
- **事后推测**：从页面特点推测可能受其影响。
- **缺失**：暂时无法取得。

请输出“文件或会话位置 → 证据 → 对哪个页面/决定有影响”。不要编造过去的设计过程，不要求披露隐藏思维链；需要的是可见记录、产物和简短设计理由。旧过程不可恢复时，从现在的基准开始记录即可。

Hermes 官方文档区分会话、项目上下文、技能和持久记忆；记忆是有界的笔记，不能当成完整项目档案。[Persistent Memory](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory)

**本地核对说明：** 本项目当前存在未提交的 `docs/ui/prototype/`。其 README 自述为单文件原型，并提及 `design-taste-frontend`、布局 seed 与保留色板/字体的参数。本轮仅检查了该说明，未确认它就是队友的那一版、未复核视觉效果或测试结论。接收方应核对来源；不能把这些名称直接写成“用户喜欢的原因”。

## 5. 如何让 Hermes 明白你喜欢什么

### 5.1 从画面中的具体位置开始

让 Hermes 展示基准页面，给关键区域编号。先问：“最想保留哪两处？最想改哪一处？”你可以指出位置、截图圈选或描述感受，不必给出 CSS 数值。

随后把每条反馈拆开：

|内容|示例（仅示范格式，并非用户已确认偏好）|
|---|---|
|用户原话|“这个像档案纸的区域我喜欢。”|
|页面证据|基准结果页，主体区域 A|
|待核实解释|可能喜欢暖色、纸面边界、排版层级，或这三者组合|
|本轮对照|保持内容与布局，只比较主体区域边界的两种处理|
|用户选择|原样保留 / 选变体 / 都不对 / 暂时说不清|
|可复用规则|确认后写清在什么页面、哪些组件上采用；标明例外|

“喜欢暖色”和“更容易找到结论”分别属于视觉偏好与使用目标，要分别记录。用户一句“不错”只表示对当前样例的反馈，不能自动批准全站字体、全部交互或所有新增页面。

### 5.2 用有限对照定位偏好

采用“原版 + 一个变体”，确有必要再加第二个变体；固定同一案件、文案、屏幕尺寸和状态，每次只改变一个关键维度。比如保持颜色不变，比较信息密度；或保持布局不变，比较标题字体。

不要要求用户在三张内容和布局都不同的图里抽象选择“高级感”。也不要把每个圆角都变成必须回答的问题。Hermes 应给出推荐及原因，并优先问会影响多个页面的选择。

视觉规则必须经过一次迁移检验：用刚确认的规则处理一个未讨论过的状态，再由用户判断是否仍符合预期。识别旧页面不等于会延展新页面。

### 5.3 每轮的反馈闭环

每轮只留下五项：

1. 本轮目标及允许改动的范围。
2. 修改前后对照，以及沿用的基准版本。
3. 对应用户原话：哪些意见采纳、哪些暂缓及原因。
4. 已确认的规则、仍待验证的假设和产品约束。
5. 下一步唯一优先事项。

记录格式可放在同一个 `decisions.md` 中：`D编号 / 日期 / 页面区域 / 用户原话 / 决定 / 理由 / 状态 / 对应版本 / 替代了哪条旧决定`。状态使用“待确认、已确认、已替代、暂缓”；新决定追加替代关系，不悄悄改写旧决定。

## 6. 怎样规范化，并沿用原设计扩展页面

规范化的最小目标是：有人接手时能找到当前版本、知道允许改什么、知道怎么判断是否做对。无需先建设庞大的设计系统。

### 6.1 三类真源

|类别|真源|冲突怎样处理|
|---|---|---|
|产品行为|PRD v1.0 + 用户后续明确指令|旧原型不能覆盖需求；新偏好若会改变功能，先单独确认|
|视觉与交互决定|用户确认记录 + 对应可打开版本|截图、文字规则、源码不一致时定位版本，不能自行猜哪个有效|
|工程接口|P 发布的实际 shared schema、HTTP 契约和运行记录|设计文件不自创后端字段；缺口提交 P|

### 6.2 从现有实现中提取规则

先检查已有 CSS 变量、主题、组件和素材。记录其真实值及源文件位置，形成简明 `DESIGN.md`：

- 排版：标题/正文/注释的字体、字号、行高、字重，以及中文长文本规则。
- 色彩：背景、表面、主文字、弱文字、边框、强调、语义状态的用途。
- 布局：内容宽度、栅格、间距、边界、圆角、阴影、层级。
- 组件：输入区、按钮、结果摘要、证据、来源、未知提示、伴读、版本提示等已有组件的变体。
- 行为：展开、收起、焦点、禁用、等待、错误、返回及移动端变化。
- 保留项：用户明确喜欢的特征及其使用范围。
- 禁用/例外：用户明确拒绝的做法，以及特殊状态需要变化的地方。

若只有内联样式，先提取成文档；是否重构代码另行讨论，避免为了整理设计而重写正在满意的页面。需要机器可读变量时优先复用当前 CSS 变量；只有跨工具交换确有需要才加 tokens JSON，不能维护两套会漂移的数值。

### 6.3 用同一套组件补用户旅程

先列状态，再决定哪些需要独立页面、抽屉或局部变化。建议按下表逐组推进；已有部分核对即可，不强制重做。

|流程组|需要覆盖|主要检查|
|---|---|---|
|输入与启动|文字/材料输入、基本模式与呈现模式、必要澄清|能顺利开始，不改需求定义|
|调查中|运行、等待用户、取消中/已取消、断线恢复、到限、部分结果|真实事件与界面反馈区分|
|结果与证据|简答、证据呈现、冲突、条件、未知、仅摘要/读取失败、无结果|结论与可追溯依据都能找到|
|伴读|开始、追问/打断、返回主线、收尾、声音失败|绑定正确结果版本，可停播|
|历史与盯梢|旧报告/新版、变化说明、通知、暂停/失败/过期|不改写旧事实，失败不冒充无变化|
|横向状态|空内容、长中文、多来源、手机、键盘焦点|核心操作可达，内容不被视觉裁切|

每个状态记录：触发条件、显示信息、可用动作、下一状态、采用组件、示例数据、对应设计版本、确认状态、工程待接项。无需每个状态都画一张精修稿。

同一组比较使用同一个明确标记为 `controlled_fixture` 的案件，包含长标题、冲突、未知、多来源和摘要来源。页面上持续标出“设计原型 / 合成示例”；现有可点击行为不能被写成真实调查、真实上传或真实语音已经接通。

## 7. 怎样才算真正迁移

迁移分三级，报告时逐级说明，不能用“文件发过去了”代替成功。

|等级|要做的操作|通过标准|
|---|---|---|
|M1：成果可搬走|在另一目录或电脑获取源码、锁文件、必要素材并启动|已确认页面可打开；关键交互可重现；没有队友私有绝对路径依赖|
|M2：设计可接续|新会话只用交接包，复述保留规则，再完成一处小改动和一个新状态|用户核对保留项未漂移；新状态复用既有规则；缺失信息被显式报告|
|M3：产品可接入|唯一 W 实现者将确认设计接到项目已有 controller/API|真实接口、错误、版本与移动端旅程通过相应测试；单独报告实际完成范围|

当前先准备 M1、M2；不以迁移为由启动 M3 的正式前端改造。

### 7.1 最小交接结构

以下是 Hermes 在迭代中逐步产出的建议结构，不要求第一轮生成一堆空文件。可放在隔离设计项目的 `ui-handoff/`；进入正式仓库时按 U/W 所有权整合到 `docs/ui/` 和确认后的 `DESIGN.md`。

```text
ui-handoff/
  START-HERE.md            # 当前版本、阅读顺序、启动方式、下一步
  source/                 # 已确认源文件、锁文件、必要素材，或精确仓库引用
  baseline/               # 已确认截图及截图条件、版本
  context-manifest.md     # 原会话/技能/参考资料与证据，缺失项
  DESIGN.md               # 已确认规则、变量及组件；候选明确标出
  decisions.md            # 用户原话、决定、版本与替代关系
  state-matrix.md         # 页面/状态/动作覆盖及尚缺部分
  handoff-check.md        # M1/M2/M3 操作、实际结果和未通过项
```

若源码在 Git 中，记录仓库地址、精确提交、分支和未提交文件处理方式；收件人没有仓库访问权时，交 Git bundle 或源码归档。不要只发一个收件人无法访问的私有链接。

`context-manifest.md` 只摘录与本项目相关且可共享的配置/记忆。队友全量 `USER.md`、`SOUL.md`、数据库、密钥和其他对话不作为迁移默认内容。若关键参考不能外发，记录限制及可共享替代描述。

### 7.2 一次最小迁移演练

1. 冻结当前确认版本，先不继续改它。在新目录/电脑按 `START-HERE.md` 启动；实际命令、版本与异常写入记录。
2. 用同一浏览器条件、视口、字体、案件和页面状态截取对照图；固定或关闭动画，核对字号、间距、布局、素材和关键交互。允许记录浏览器抗锯齿等环境差异，不承诺跨平台像素完全一致。
3. 新会话不读原聊天，只读交接包。请它复述保留规则，并做一个用户指定的小调整，以及一个基准未展示的新状态，例如“来源读取失败”。
4. 用户检查是否延续了喜欢的点、是否正确呈现状态；记录通过、失败和具体偏差。原作者解释后修好，说明包仍有缺口，补写资料后再验一次。
5. 输出明确结论：“M1通过 / M2待验 / M3未做”等。不能笼统写“迁移成功”。

这项演练是本项目的验收建议。它验证可携带性与可接续性，不证明模型在所有后续设计上都会保持同样效果。

## 8. Hermes 会话与 grill-me 的使用安排

本节以 Nous Research 的 Hermes Agent 官方文档为依据；如果队友使用的是同名其他产品或不同封装，先核对版本和帮助，不直接执行这里的命令。

### 8.1 保护原会话

先记下会话 ID、工作目录和基准。官方支持查看会话列表、恢复指定会话和导出单个会话；命令是否可用，以队友安装版本的 `--help` 为准。[Sessions](https://hermes-agent.nousresearch.com/docs/user-guide/sessions)

```text
hermes --version
hermes sessions list
hermes --resume <已核对的会话ID>
hermes sessions export --help
```

确需可读会话备份时，在核对帮助后导出指定会话，优先脱敏 Markdown；记录命令实际返回的文件路径。示例：

```text
hermes sessions export --format md --session-id <已核对的会话ID> --redact
```

不要导出所有会话，不附加删除参数。导出的聊天仅作为记录，不能代替源码、图片和运行依赖。恢复旧会话后也要核对实际目录和配置，不能认定环境完全不变。

### 8.2 安装技能，但不把安装变成前置障碍

包内 [skills/grill-me/SKILL.md](skills/grill-me/SKILL.md) 是从用户本机复制的完整中文适配版，并保留来源说明。它不依赖另一份 `grilling` 文件；本轮未改动技能正文，也未在队友 Hermes 上安装或实测。

官方当前 [grill-me](https://github.com/mattpocock/skills/blob/main/skills/productivity/grill-me/SKILL.md) 是调用 [grilling](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md) 的入口。若改用官方原版，应一起检查依赖与工具调用适配，不能只看到名字就判定可用。

推荐步骤：

1. 检查当前 Hermes 实例/profile 的真实技能目录，查看是否已有同名技能。默认目录是 `~/.hermes/skills/`；自定义 home/profile 时不能照抄默认值。
2. 没有同名技能时，将包内整个 `skills/grill-me/` 目录复制进去。若已有版本，先比对和保留原件，不静默覆盖。
3. 查看 `hermes skills list`，或在会话使用 `/skills search grill-me`；再确认能读取技能全文。
4. 让它对当前设计提出一轮有依据的问题，并等待回答。只有文件存在、列表可发现、实际遵守提问协议都验证后，才记录“安装可用”。

官方说明技能通常在新会话生效，也提供当前会话刷新相关方式；为保留原设计上下文，不要直接 `/reset`。先在原会话读取包内 `SKILL.md` 临时使用，或在核对本机帮助后采用支持的刷新方式。[Working with Skills](https://hermes-agent.nousresearch.com/docs/guides/work-with-skills)

### 8.3 本项目如何使用提问协议

- 每轮挑当前最重要、前置事实已明确的 1–3 个问题；其余记入待问项，后续推进。此条按本项目 U 任务书控制阅读负担。
- 先查文件、界面和现有决定；不要把可查的路径、组件名和依赖版本反问用户。
- 给推荐与具体图示依据，但让用户选择；允许“不确定，先保留”。
- 只澄清尚未确认的视觉/交互，不从头拷问整个产品，也不因一个次要偏好未定而阻塞已明确区域。
- 修改前复述本轮范围并等待确认；用户确认后执行该范围，更新产物，再做下一轮。
- 用户偏好记在本项目文件中，不把叶泽森的偏好写成队友本人全局画像。

不要为了加入这份说明而直接新建最高优先级 `.hermes.md`、覆盖原 `AGENTS.md` 或改队友全局 `SOUL.md`。先显式读取本文件；若将来需要自动加载，检查既有上下文加载规则再合并入口。[Context Files](https://hermes-agent.nousresearch.com/docs/user-guide/features/context-files)

## 9. 与侦探 Agent 正式开发的边界

本包附 [PRD v1.0 快照](references/AI开发需求文档.md)。用户后续明确指令优先；快照不是工程最新状态索引。

本轮 Hermes 的角色是独立设计收敛。允许读取和整理现有网页原型；修改原型需先确认范围，并在隔离副本中进行。正式仓库的 U 任务仍是先设计、不编码产品页面、不改接口。不得因“原型本身有代码”就接管 `src/web/`、公共配置或后端。

必须保留的关键约束：

- 基本模式与呈现模式分开，呈现模式在任务开始时选择；不能私加任务中任意切换的产品需求。
- 结论、关键条件、未知、来源可找到；全文、摘要与读取失败区分。
- 正式调查进度来自真实事件，不能靠预设答案、假搜索、假通知制造完成感。
- 缺信息、等待、取消、到限、部分结果、失败与空结果都有合理呈现。
- 伴读可打断、返回、收尾；声音点击才播、可停止，换段不叠音。
- 旧报告与旧伴读保留原版本；新报告有变化说明，能返回旧版。
- 桌面之外覆盖 360px 手机核心流程、中文长文本与可见操作反馈。

已有用户满意的设计优先作为视觉起点。旧 U 任务中“从头做布局比较”的安排，在本次情境下改为“核对已有版，必要时做局部对照”；这不代表已有稿已经被用户全量批准。

设计确认后交唯一 W 实现者接到现有 controller；P 负责 shared、平台、根依赖与契约变更。不能让另一个 Agent 按截图再自由发挥一遍。没有模块派发记录时不进入正式代码写入。

## 10. 第一轮与阶段交付标准

**Hermes 第一轮只交付：**

1. 不超过一屏的现状：已读文件、找到的基准、可恢复副本位置、已知/未知的来源和环境。
2. 对现有页面的 2–3 条“可能值得保留”的观察，全部标为假设，不替用户确认。
3. 当前最重要的 1–3 个问题，附推荐和具体位置；然后等待用户回复。

没有读取到网页或源码时，如实说明缺什么，不凭这份文档想象现有视觉。文件能查到的事实先自己查；只有访问不到的资料才请用户提供位置或文件。

**阶段完成的检查：**

- [ ] 满意基准、源码和依赖可恢复，且未提交修改已纳入。
- [ ] 喜欢/不喜欢的具体位置、原话与可用规则有对应关系。
- [ ] 一次局部迭代已获用户确认，基准之外至少一个新状态验证了延续性。
- [ ] 主要流程和异常状态有覆盖清单，未做部分明确。
- [ ] 交接入口、源文件、设计规则、决策和版本互相对应。
- [ ] M1/M2/M3 分别有实际结果，未执行项不写通过。
- [ ] 设计确认与功能、API、部署验收分开记录。
